# 회원 탈퇴 구현 중 점검

이 문서는 구현을 위한 작업 목록이며, 현재 탈퇴 기능이 완성되었거나 운영 개인정보 처리방침이 확정되었다는 뜻이 아니다. 미완성 상태에서 사용자 데이터를 지우는 API를 열지 않는다.

## 확인된 요구사항

- 탈퇴 요청에서 2차 비밀번호를 새로 확인한다. 이전에 로그인하면서 입력한 PIN이나 오래된 세션 검증 결과만으로 대신하지 않는다.
- 본인이 소유한 공유 가족 카테고리는 다른 활성 멤버를 선택해 소유권을 이전한다. 다른 멤버가 올린 사진은 보존하고, 탈퇴자가 올린 공유 사진도 이전받은 카테고리 소유자에게 넘겨 보존한다. 다른 사람의 카테고리에 올린 공유 사진은 그 활성 카테고리 소유자에게 이전한다. 이전할 활성 소유자가 없으면 자동 삭제하지 않고 중단한다. 공유되지 않은 개인 사진은 이전 대상이 아니다.
- 본인이 소유한 가계부·여행 공유 그룹에 다른 멤버가 있으면 다른 활성 멤버에게 소유권을 이전한다. 이전 대상이 같은 이름의 그룹을 갖고 있거나, 다른 사람의 공유가 남아 있는데 이전 가능한 멤버가 없으면 자동으로 삭제하거나 덮어쓰지 않고 중단한다.
- 탈퇴자가 소유하고 다른 사람에게 공유 중인 여행 계획과 사진은 선택한 기존 공유 수신자에게 이전한다. 그룹 소유자 선택과는 별개이며, 다른 수신자의 접근도 보존할 수 있는지 확인한다. 공개 전시·커뮤니티나 공개 지도 링크로만 공유 중인 계획은 먼저 회원에게 직접 공유해 이전 대상을 정해야 한다. 이전할 때 기존 공개 전시·커뮤니티 공개와 탈퇴자의 공개 지도 링크는 해제하고, 새 소유자가 공개 여부를 다시 정한다.
- 카카오를 연결한 기존 계정은 탈퇴 이전까지 기존 ID·비밀번호 로그인과 카카오 로그인을 함께 유지한다. 탈퇴 시 카카오 서버의 연결 해제를 확인해야 한다.
- 사용자가 카카오 설정에서 직접 연결을 끊으면 기존 ID·비밀번호가 있는 계정은 일반 로그인과 데이터를 유지한다. 카카오 전용 계정의 탈퇴는 인증 이메일 소유 확인과 2차 비밀번호 확인을 모두 거쳐 진행한다. 웹훅을 받았다는 이유만으로 계정이나 자료를 자동 삭제하지 않는다. 이메일 확인·이전 대상 선택 화면과 API는 격리 테스트용으로만 연결했고, 연결 끊김 감지와 운영용 공개 API는 아직 준비되지 않았다.
- 사용자는 탈퇴 승인 즉시 운영 서비스의 본인 자료 삭제 절차를 시작하고, 탈퇴자의 정보가 포함될 수 있는 전체 백업은 최대 30일 이내에 폐기하는 방침을 선택했다. 법적으로 보존해야 하는 자료·기간은 서비스의 실제 운영형태를 기준으로 확인해야 한다. 아직 전체 데이터 삭제 및 백업 자동 폐기는 구현·적용되지 않았다.
- 관리자는 다른 활성 관리자가 한 명 이상 있을 때 탈퇴를 허용한다. 마지막 관리자에게는 먼저 다른 관리자를 지정하도록 안내한다. 기존 관리자가 다른 활성 사용자에게 관리자 권한을 부여하는 화면과 API를 추가했으며, 관리자 화면 접근 인증과 새로운 2차 비밀번호, 권한 범위 확인 및 감사 기록을 사용한다. 권한을 받은 사용자는 다시 로그인해야 하며, 이 화면에서 관리자 권한을 회수할 수는 없다.
- 탈퇴자의 로그인 및 관리자 감사 기록은 아이디·IP·접속 기기와 자유 텍스트 등 식별 정보를 익명화하고 행위 유형과 시각만 보존한다. 법령상 별도 보존이 필요한 자료는 실제 운영 방식에 따라 검토한다.
- 계정이 완전히 지워진 뒤 예전 아이디를 재입력하는 실패는 다른 미등록 아이디와 구분할 수 없으므로, 사용자가 **모든 미등록 아이디의 로그인 실패 기록도 익명화**하도록 선택했다. 기록의 보안 조사 정보는 줄지만 기존 로그인 시도 차단은 유지한다. 차단 기능은 감사 기록과 별개로 IP별 임시 카운터·차단 상태를 보유하며 차단 기간은 24시간이다. Redis 키는 TTL을 사용하고 만료된 프로세스 메모리는 주기적으로 정리한다. 실패가 여러 시점에 반복되면 최초 실패 시각부터 24시간과 차단 종료 시각은 다를 수 있다.

## 보존·정리 대상

| 영역 | 현재 확인한 의존관계 및 구현 시 주의사항 |
| --- | --- |
| 계정·보안 | 사용자, 소셜 연결, 이메일 토큰, 레이아웃, 문의와 첨부파일, 초대, 로그인 기록, `persistent_logins`가 서로 다른 방식으로 사용자를 참조한다. Redis 세션은 현재 사용자별 조회 인덱스가 없는 `RedisSessionRepository`다. 인증 API 요청마다 DB에서 활성 상태를 확인하는 필터를 추가했지만, 이미 실행 중인 요청의 중단·작업 정리 및 탈퇴와의 트랜잭션 경계는 별도 검증이 필요하다. |
| 가족 앨범 | `family_categories` 소유자, `family_category_members`, `family_albums` 소유자, `family_media_assets` 업로더가 각각 다를 수 있다. 카테고리를 일괄 삭제하거나 소유자 ID로 객체 prefix를 삭제하면 다른 사람의 사진이 손상될 수 있다. |
| 가계부·공유 | 거래, 변경 이력, 정기결제, 분류, 이미지/OCR/AI 이력과 원본 파일, 사용자 목표·설정이 있다. `record_shares`의 수신자가 승인해 독립 등록한 거래는 원본 소유자와 다를 수 있으므로 일괄 삭제하지 않는다. |
| 여행·기록 지도 | 여행 계획·경로·기록·사진·클러스터·지도 공유 및 기록 지도 장소·방문·사진·모음·공유를 함께 검토한다. 여행 그룹의 소유자와 멤버, 원본 업로더 및 공유 대상자는 다를 수 있다. |
| 드라이브·파일 | 파일·버전·다운로드 링크·공유·접근 기록과 원본 객체가 분리되어 있다. 여행과 드라이브가 같은 저장 객체를 참조할 수 있으므로 참조 확인 없이 삭제하지 않는다. 로컬 파일, MinIO 객체, 파생 썸네일과 중단된 업로드도 확인해야 한다. 가족·여행·드라이브에서 발급된 PUT 서명 URL은 계정 비활성화만으로 회수되지 않으며 설정 기본값이 6,000초이고 변경 가능하다. 준비 후 완료하지 않은 객체 키도 현재 영속 관리되는지 확인해야 하므로 유효기간이 남은 업로드의 차단·만료 후 재확인 전에는 객체 정리를 완료했다고 표시하지 않는다. |
| 검색·비동기 작업 | 진행 중인 이미지/엑셀/클러스터 작업이 삭제 뒤 데이터를 다시 기록하지 않게 차단한다. 이미 외부 AI 서버에 전달된 요청은 로컬 DB에서 삭제해도 회수됐다고 단정할 수 없으므로 제공자의 처리 중단·보존·삭제 정책을 확인한다. 가계부 임베딩 outbox와 외부 검색 인덱스의 원문·벡터 삭제 및 재시도를 누락하지 않는다. |
| 백업 | DB와 MinIO 전체 백업에는 여러 사용자의 자료가 섞인다. 사용자가 선택한 최대 30일 이내 폐기와 복원 시 탈퇴 내역 재적용, 법적 보존 예외를 실제 운영 백업 시스템에 맞춰 구현·검증해야 한다. 로컬·원격 기본 보관소·날짜별 archive·보조 복사본 및 다운로드한 파일의 처리 범위를 확인해야 하며, 현재 코드에 이 방침을 보장하는 기능은 없다. |

추가 확인: 계정 비활성화만으로 `travel_map_share_links`, `drive_download_links`나 여행 공개 전시가 자동 철회되지는 않는다. 내부 탈퇴 단계에 해당 사용자의 공개 링크·여행 공개 및 커뮤니티 공개 중단을 추가하고 관련 생성·수정 요청이 계정을 먼저 잠그게 했다. 다만 이미 발급된 다운로드 URL은 만료 전까지 회수할 수 없고 Redis가 끊긴 동안의 공개 캐시 정리도 보장되지 않는다. 관련 저장소·캐시와 다른 공개 경로까지 실제 환경에서 검증하기 전에는 탈퇴 후 외부 공유가 완전히 차단됐다고 간주하지 않는다.

운영 예시에서 백업 작업은 별도 원격 에이전트에 위임되며, 이 저장소의 `RemoteBackupAgentClient`에는 생성·목록·복원만 있고 폐기 계약은 없다. 사용자는 우선 Calen 측 구현을 진행하도록 선택했다. 에이전트와 원격 저장소의 폐기 기능 및 백업 복원 절차가 확인되기 전에는 전체 보관소에 30일 정책이 시행된 것으로 간주하지 않는다.

별도 프로젝트의 `C:\project\pri-serv\backup\server-recovery-2026-10-07-ssd-drive\backup-agent`에서 Calen이 호출하는 경로와 유사한 에이전트 사본을 찾았지만, 사용자는 이 사본이 현재 운영 버전인지 알지 못한다. 운영 서버의 실행본과 저장소 범위가 확인되기 전에는 해당 사본을 운영 코드로 간주하거나 30일 삭제를 적용하지 않는다. 이 사본은 수정하지 않았다.

## 운영 전 법적 검토

- [개인정보 보호법 제21조](https://www.law.go.kr/lsLinkProc.do?joNo=002100&lsClsCd=L&lsNm=%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4+%EB%B3%B4%ED%98%B8%EB%B2%95&mode=11)는 개인정보가 불필요해지면 지체 없이 복구·재생되지 않도록 파기하고, 다른 법령에 따른 보존이 필요한 경우에는 분리 저장·관리하도록 규정한다. 실제 적용 범위와 예외는 운영 형태에 맞춰 검토해야 한다.
- 사용자가 선택한 **백업 최대 30일**은 운영 목표이지, 모든 개인정보에 대해 30일 보관을 허용하는 법적 근거로 단정할 수 없다. 백업·복원·법령상 보존 예외를 검토하고 실제 시행 여부를 처리방침에 정확히 공개하기 전에는 준수를 주장하지 않는다.
- 가계부에 사용자가 입력한 거래와 서비스 운영자가 직접 수행한 전자상거래는 다를 수 있다. 확인되지 않은 일률적인 3년·5년 보존기간을 탈퇴 화면이나 코드에 넣지 않는다. 개인정보 처리방침에는 실제 처리 목적·보유기간 및 파기 방식 등 필요한 사항을 반영해야 한다([개인정보 보호법 제30조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1025127663)).

## 원자성 및 장애 처리

1. 사용자에게 확인된 처리 범위와 공유물 이전 대상을 보여주고, 최종 요청에서 PIN을 다시 검사한다. 소유자·이전 대상·멤버십은 트랜잭션 안에서 재검증한다.
2. 중복 요청을 방지하고 새 인증·쓰기·진행 중 작업을 차단한다. 모든 노드와 기기의 기존 세션 및 자동 로그인 토큰도 무효화한다.
3. 카카오 등 외부 연결 해제 및 DB/객체/인덱스 삭제는 하나의 DB 트랜잭션으로 묶을 수 없다. 실패와 타임아웃, 프로세스 중단 후에도 재시도·정합성 확인이 가능한 지속 작업 상태가 필요하다. 민감한 토큰과 주소·사진 내용을 로그에 남기지 않는다.
4. 다른 사용자 자료의 소유권 및 공유 범위를 보호하면서 각 영역을 정리한다. 최종 성공은 모든 필수 삭제와 외부 연동 처리가 확인된 뒤에만 표시한다. 백업은 실제 정책에 따라 별도 잔존 기간과 복원 절차를 안내한다.
5. 탈퇴·외부 연결 해제 웹훅·재가입·복원 순서가 서로 경합할 때 중복 처리나 탈퇴 자료 재생성이 발생하지 않는지 격리 환경에서 테스트한다.

## 이번에 준비된 개별 부품

- 내부 탈퇴 시작이 확정되는 트랜잭션에서 표시 이름·일반 비밀번호 해시·2차 비밀번호 해시·개인 설정, 과거 이메일 인증 대상 주소와 인증 토큰·탈퇴 복구 증명, 소셜 계정에 저장된 이메일을 지운다. 거래나 공유 처리 실패 등으로 트랜잭션이 롤백되면 이 변경도 함께 롤백된다. **로그인 ID·현재 이메일은 안전한 식별자 재사용 정책이 완성될 때까지 남고**, 카카오 회원번호도 연결 해제 및 재연결 차단에 필요해 남는다. 따라서 이 단계는 개인정보 전체 삭제나 탈퇴 완료가 아니다. 운영 공개는 여전히 차단되어 있으며 실제 MariaDB 경합과 모든 인증 경로 검증이 필요하다.

- `KakaoWithdrawalCleanupExecutor`: 카카오 연결 해제 작업 한 건을 DB 트랜잭션 밖에서 처리하는 부품이다. 외부 호출 전 별도 트랜잭션에서 진행 중인 탈퇴 요청, 비활성 계정과 원래 카카오 연결, 암호화된 작업 대상과 소유권, 충분히 남은 임대 시간을 다시 확인한다. 계정·대상이 맞지 않으면 외부 호출 없이 수동 확인으로 남기고, 임대가 부족하면 재획득을 기다린다. 응답이 유실된 경우 성공으로 간주하지 않고 제한된 횟수만 재시도한 뒤 운영자 확인을 기다린다. 실제 호출 전후 구형 노드나 수동 DB 변경을 포함한 경합, 대상 앱과 관리자 키가 올바른지 및 이미 해제된 계정을 어떻게 확인할지는 실연동 시 별도 검증이 필요하다. 공개 탈퇴 요청에는 연결되지 않았다.
- 카카오 회원번호는 앱별 식별자이므로 테스트 앱과 운영 앱을 바꿔 가며 같은 번호를 해제 대상으로 취급해서는 안 된다. 아래 `V20261103_050` 항목처럼 새 로그인 시 앱 ID를 검증해 기록하는 절차를 준비했지만, 미로그인 기존 계정은 여전히 미확인이며 설정된 어드민 키가 해당 앱의 키인지도 프로그램이 증명하지 않는다. 이미 연결이 해제된 사용자에 대한 오류도 단독으로 삭제 성공의 증거로 간주하지 않는다. 실제 검증과 전체 탈퇴 작업이 완료되기 전에는 내부 작업자를 운영에 켜면 안 된다.
- `WithdrawalCleanupWorker`: 내구성 있는 카카오 해제 작업의 재시도와 제한된 일괄 처리를 위한 **격리 테스트 전용** 실행 부품이다. `internal-workflow-enabled`와 `cleanup-worker-enabled`를 둘 다 명시적으로 켠 테스트 환경에서만 생성되며 기본적으로 동작하지 않는다. 별도 스레드에서 작업해 다른 스케줄러를 가로막지 않고, 오류·중복 실행·프로세스 종료는 기존 작업 임대와 재시도로 처리한다. 파일·검색·백업 정리, 운영 관찰·수동 확인, 실서비스 연결 해제 검증이 아직 없으므로 운영에서 설정을 켜서는 안 된다.
- `AccountWithdrawalStartService`: 정확한 PIN을 다시 검증하고, 가족 앨범·공유 그룹 이전과 계정 비활성화, 인증 토큰 무효화, 공유 요청·가계부 거래와 변경 이력·정기거래 규칙과 발생 내역·분류와 결제수단 정리 및 암호화된 카카오 해제 작업 등록을 한 DB 트랜잭션으로 묶는 내부 통합 단계다. `READ COMMITTED`를 명시하고 실제 연결의 격리 수준도 확인해, 기존 반복 읽기 스냅샷 때문에 잠금 대기 중 확정된 공유 자료를 놓칠 수 있는 외부 트랜잭션에서는 실행하지 않는다. 이미지 원본·사진·여행·파일 등 나머지 자료의 실제 삭제와 후속 실행기는 아직 없으므로 `app.account-withdrawal.internal-workflow-enabled=true`인 격리 테스트에서만 생성되며 운영 API로 호출할 수 없다. 단일 트랜잭션에서 자료량에 비례하는 조회·정리를 수행하므로 대량 데이터에서는 별도 배치화와 운영 DB 잠금·성능 검증도 필요하다. 운영에서 이 내부 테스트 설정을 켜거나 완료된 탈퇴로 표시해서는 안 된다. 다른 활성 관리자가 없으면 관리자 탈퇴를 거절한다.
- 탈퇴 화면에는 공유 가족 앨범·공유 그룹·여행 계획마다 이전받을 회원 선택과 최종 PIN·동의 확인을 연결했다. 요청 API는 기본적으로 503을 반환하며, `withdrawal-integration` 프로필에서 `app.account-withdrawal.internal-workflow-enabled`와 `app.account-withdrawal.integration-http-enabled`를 모두 명시적으로 켠 **격리 DB 전용 통합 환경**에서만 내부 시작 단계가 연결된다. 이 프로필과 설정을 운영 DB에 사용해서는 안 된다. 요청을 접수해도 파일·백업·외부 저장소 정리까지 끝났다는 뜻은 아니며 완료 여부를 별도로 확인해야 한다. 사용자 화면, 요청 인증·CSRF와 소유권 선택의 실제 통합 검증은 아직 필요하다.
- 같은 격리 환경의 관리자 접근·사용자 관리에는 탈퇴 요청별 작업 종류와 상태의 읽기 전용 집계를 추가했다. 관리자 권한과 관리자 화면의 2차 비밀번호 인증이 필요하며, 사용자 ID·파일 경로·암호화된 작업 내용은 응답하지 않는다. 목록화 항목은 삭제가 아니고 성공한 작업 수만으로 전체 탈퇴 완료를 판정하지 않는다. 이 화면과 API도 통합 검증 전이다.
- 격리 관리자 화면에는 실패한 카카오·가계부 이미지·문의 첨부 정리 중 **미리 지정한 일시 오류만** 다시 대기시키는 기능을 추가했다. 관리자 권한·접근 인증과 새로운 PIN을 확인하고 요청·작업·비활성 계정의 관계를 잠가 재검사한 뒤 감사 행위와 재대기를 함께 기록한다. 대상 경로와 암호문은 공개하지 않으며, 실행기는 재시도 시에도 기존의 대상·공유 참조 검증을 수행해야 한다. 잘못된 대상·참조·출처나 카카오 재연결이 불명확한 작업은 이 버튼으로 해제할 수 없다. 재대기는 외부 삭제 완료가 아니며 운영에서는 비활성이다.
- 관리자 지정은 대상 계정이 활성 상태이고 탈퇴 처리 중이 아닌지 확인하고, 권한 변경·자동 로그인 토큰 무효화·감사 기록을 한 트랜잭션으로 처리한다. 기존 세션에는 권한을 소급 부여하지 않는다. 다른 관리자의 권한 해제나 기존 계정의 재로그인까지 자동화하지 않으며, 실제 운영 DB에서 관리자 지정과 탈퇴가 동시에 발생하는 경합은 별도로 확인해야 한다.
- `KakaoWithdrawalRecoveryService`: 카카오 전용 활성 계정의 기존 인증 이메일로 제한 시간의 일회용 탈퇴 확인 링크를 발급하고, 이후 PIN까지 확인하는 내부 부품이다. 링크만으로 로그인하거나 삭제하지 않으며, 이메일·비밀번호·PIN 변경 및 관리자 비활성화 때 미사용 링크를 무효화한다. 이메일 발급·공유 항목 조회·이전 대상 선택·최종 탈퇴 요청 화면과 API를 연결했지만 위의 `withdrawal-integration` 프로필과 두 설정이 함께 켜진 격리 환경에서만 요청이 가능하다. 운영에는 공개하지 않는다. 실제 SMTP·카카오 연결 상태 확인 및 통합 검증은 여전히 필요하다. 웹훅이 소셜 연결 자체를 삭제하면 확인 대상 여부를 잃지 않도록 연결 끊김 상태 모델도 필요하다.
- `V20261105_055` 이후 카카오 전용 탈퇴 복구의 PIN 실패 횟수와 잠금 만료를 인증 증명에 저장한다. 증명을 다시 발급해도 기존 횟수와 잠금을 이어받으며, 사용자와 인증 증명을 잠가 다중 요청·노드에서 확인한다. 발송 실패 시 기존 확인 링크는 유지한다. 이는 SMTP 실연동과 운영 탈퇴 활성화 조건을 대신하지 않는다.
- `V20261105_056` 이후 격리 복구 API는 DB의 단기 HMAC 지문으로 전체·접속 IP·입력 이메일별 요청을 제한하고 만료된 지문을 분할 폐기한다. 원본 IP와 이메일은 제한 테이블에 저장하지 않으며, 계정 존재 여부와 관계없이 이메일별 제한에는 같은 접수 응답을 보낸다. `app.account-withdrawal.recovery-trusted-proxies`에는 신뢰할 프록시의 정확한 IP만 쉼표로 지정한다. 지정한 프록시가 `X-Real-IP`를 덮어쓰고 백엔드 직접 접근이 막혀 있어야 하며, 그렇지 않으면 실제 이용자 구분이나 위조 방지가 보장되지 않는다. 다중 노드 키 일치, 프록시 체인, MariaDB와 실제 트래픽 검증은 아직 필요하다.
- 격리 복구 기능의 만료된 이메일 증명은 250건씩 정리한다. 유효한 증명, 아직 유효한 PIN 실패·차단 시간과 상태가 불일치한 기록은 지우지 않아 증명 재발급이나 정리 배치로 잠금이 초기화되지 않도록 한다. 이는 테스트용 복구 기록 정리이며 백업이나 다른 개인정보의 삭제 완료를 뜻하지 않는다.
- [카카오 웹훅 명세](https://developers.kakao.com/docs/ko/kakaologin/callback)에 따르면 기존 연결 해제 웹훅은 대표 어드민 키와 앱 ID를 확인해야 하며 요청에 이벤트 발생 시각이 없다. 반면 계정 상태 변경 웹훅의 서명된 `User Unlinked` 이벤트에는 이벤트 시각과 고유 ID가 있으므로, 재연결 이후 지연된 해제 알림을 잘못 적용하지 않도록 서명·발급자·수신 앱·발생 순서·중복을 검증하고 실제 카카오 연결 상태와 정합성을 확인하는 설계가 필요하다. 두 방식의 응답 규격도 다르다. 아직 수신기·재처리·운영 설정을 구현하거나 검증하지 않았으며 알림만으로 계정을 삭제하지 않는다.
- 정기거래 정리는 탈퇴가 진행 중인 비활성 계정에만 허용하고, 다른 사람의 정기거래와 이미 생성된 일반 거래는 수정하지 않는다. 외부 검색 인덱스가 과거에 사용되었을 수 있으므로 현재 인덱스 기능을 꺼 둔 경우에도 삭제 대기열에 규칙별 작업을 남긴다. 대기열 등록은 외부 검색에서 실제로 삭제됐다는 뜻이 아니며, 재시도·최종 확인과 MariaDB 실검증은 남아 있다.
- 일반 거래 정리는 해당 소유자의 휴지통을 포함한 거래와 변경 이력만 삭제한다. 다른 사용자가 공유를 수락해 자기 가계부에 독립 등록한 거래는 유지한다. 거래 쓰기와 엑셀 가져오기 및 공유 수락은 계정을 먼저 잠가 비활성화 이후 새 거래가 만들어지지 않도록 한다. 검색 대기열이 이미 알고 있는 과거 삭제 기록도 다시 정리하도록 예약하지만, 인덱스 동기화가 꺼졌을 때 원본과 대기열에서 이미 사라진 벡터는 현재의 ID 단위 삭제 API만으로 누락 여부를 증명할 수 없다. 수신 서버의 사용자별 전체 삭제·검증 계약이 확인되기 전에는 검색 인덱스 정리가 완료됐다고 간주하지 않는다.
