# AI 분석 회귀 오류 수정

2026-10-04. 운영 데이터나 제공자 설정을 변경하지 않고, 저장소 코드와 로컬 테스트로 원인을 재현하고 수정했다.

## 확인된 원인

| 증상 | 원인 | 수정 |
|---|---|---|
| 이미지 분석 접수 시 `Row was updated or deleted ... LedgerImageAnalysisRequest` | 성능 개선에서 `@Version`을 도입했지만, 프롬프트 저장 후 `save()` 반환 객체를 사용하지 않았다. 다음 원본 이미지 참조 저장에서 이전 버전으로 다시 저장했다. | 프롬프트를 최초 생성과 함께 저장한다. 원본 참조는 상태를 덮어쓰지 않는 별도 갱신으로 연결하고, 최신 기록을 다시 조회한다. |
| LLM은 완료됐으나 가계부 분석이 계속 PROCESSING | 작업 입력 저장으로 버전이 증가했지만, 비동기 작업은 이전 객체로 완료를 저장했다. 예외 처리도 같은 객체로 FAILED를 저장해 다시 충돌했다. `FutureTask` 내부 예외는 별도로 확인하지 않아 실행기 밖으로 드러나지 않았다. | 입력·완료·실패를 ID와 소유자, 현재 상태를 기준으로 원자적으로 갱신한다. 예기치 않은 작업 종료도 기록한다. |
| 같은 조건의 분석이 여러 번 실행된 뒤 최신 결과 조회 오류 | 정렬만 있고 결과 수 제한이 없는 조회를 단일 `Optional`로 받았다. 여러 행이면 `NonUniqueResultException`이 발생했다. | 완료·진행 중 최신 조회에 `Limit.of(1)`을 적용한다. |

수정 전 H2 실제 JPA 저장소와 서비스 호출을 연결한 첫 4개 테스트 중 3개가 실패했다. 이미지 원본 저장, 가계부 완료 저장, 제공자 오류의 실패 저장에서 모두 동일한 낙관적 잠금 예외가 재현됐다. 임시 이미지 경로는 통과했다.

기존 서비스 단위 테스트는 `save()`에 넘긴 객체를 그대로 반환하도록 모킹하고 있었으므로, 실제 JPA의 병합 객체와 버전 변경을 검증하지 못했다. 새 테스트는 테스트 전체를 하나의 트랜잭션으로 감싸지 않아 비동기 작업처럼 저장마다 커밋되도록 한다.

Spring Data JPA는 기존 엔티티 저장 시 병합을 사용한다. 저장 결과와 버전 관리는 [엔티티 저장 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/entity-persistence.html), 결과 제한은 [조회 제한 문서](https://docs.spring.io/spring-data/jpa/reference/3.5/repositories/query-methods-details.html#repositories.limit-query-result)를 참고했다.

## 유지한 동작과 안전 장치

- 이미지 분석은 기존 멀티모달 LLM API를 사용한다. 모델·프롬프트 정책·제공자 주소·키는 바꾸지 않았다.
- MinIO 원본 참조, 임시 파일 대체 경로, 작업 대기열, 제공자 실행 제한 및 서버 간 작업 소유권은 유지했다.
- 이 비동기 처리에서는 원격 추론 동안 DB 쓰기 트랜잭션을 유지하지 않는다. 상태 쓰기는 짧은 별도 트랜잭션으로 실행한다. 읽기 전용 복구 스캔에서도 실패 상태를 커밋할 수 있다.
- 상태 쓰기는 `id`, `owner_id`, `status=PROCESSING`을 함께 검사하고 버전을 증가시킨다. 이미 완료·취소됐거나 삭제된 요청은 늦은 결과·실패로 덮어쓰거나 다시 생성하지 않는다.
- 이미지 취소는 상태를 먼저 커밋한 후 작업을 중단한다. 중단 때문에 발생한 예외가 취소를 FAILED로 바꾸지 않는다.
- 원본 업로드 중 취소가 발생해도 참조 연결이 버전 충돌을 일으키지 않는다. 취소 상태와 원본을 유지하고 추론을 시작하지 않는다. 이미 삭제된 기록의 새 원본은 연결하지 않고 정리한다.
- 이미지 결과 JSON 직렬화에 실패하면 빈 결과를 COMPLETED로 저장하지 않고 FAILED로 처리한다.
- 작업 종료 로그에는 이력 ID와 예외 종류를 남긴다. 추가한 로그에 프롬프트·거래 내용·토큰은 넣지 않는다.
- 추출한 거래 후보는 사용자가 검토하는 기존 흐름을 유지한다. 분석 완료만으로 가계부 거래를 생성하지 않는다.

## 화면 흐름 점검

가계부 분석과 이미지 분석은 완료·실패 상태를 주기적으로 조회한다. 일반 분석 조회 간격은 2초이며, 동시 GET 합치기는 완료 응답을 캐시하지 않는다. 서비스 워커도 `/api/` 요청은 캐시하지 않는다. 이번 재현에서는 화면 캐시가 아니라 DB의 상태·결과 저장 실패가 PROCESSING 유지의 원인이었다. 운영 환경의 실제 표시 시간은 별도 확인이 필요하다.

## 검증

`LedgerAiJobPersistenceTest` 20개가 모두 통과했다. 다음 항목을 실제 H2 JPA 저장소로 확인했다. LLM과 이미지 저장소는 테스트 대역을 사용했다.

- MinIO 참조 저장 경로 및 임시 이미지 경로의 접수·완료
- 가계부 LLM 완료 결과와 제공자 실패의 후속 상태 조회
- 이미지 제공자 실패의 상태 조회
- 대기 중 취소, 다른 서버의 취소 이후 도착한 이미지 결과
- 원본 이미지 업로드 중 취소, 저장된 원본 참조를 이용한 재시작 복구
- 원본 이미지 업로드 중 삭제 시 새 객체 정리 및 기록 재생성 방지
- 분석 중 삭제된 이미지·가계부 요청이 재생성되지 않음
- 다른 작업에서 이미 완료한 결과를 늦은 실패가 덮어쓰지 않음
- 재시작 상황의 진행 중 가계부 작업 복구
- 복구 입력이 없는 구형 작업의 읽기 전용 스캔 중 FAILED 전환
- 같은 조건의 완료 이력이 여러 건일 때 최신 한 건 조회
- 이미지 후보 날짜·시간·금액·분류의 JSON 저장 및 조회, 거래 자동 저장 없음
- 이미지 및 가계부 결과 직렬화 실패 처리
- 소유자 범위 검사와 버전 증가

- 백엔드 전체 테스트 434개 통과, 실패·오류·스킵 0개 (`gradlew.bat test bootWar`)

코드·테스트·문서만 수정했다. 위 검증은 커밋·푸시 전에 수행했으며, 운영 배포는 별도 절차로 진행해야 한다.

## 운영 적용 시 확인

1. 수정된 백엔드를 배포해야 실제 서비스에 반영된다. 이번 작업에서는 운영 서버에 배포하거나 운영 DB를 수정하지 않았다.
2. 기존 성능 개선 마이그레이션 `V20261003_023`~`027` 적용 여부, 특히 작업 소유권 테이블과 버전 컬럼을 확인한다. Hibernate 자동 갱신만으로 마이그레이션 적용을 판단하지 않는다. 이번 수정에 새 스키마 변경은 없다.
3. 이미지 한 장 분석 후 접수 ID로 `/api/ledger/image-analysis/history/{id}`가 COMPLETED와 거래 후보를 반환하는지 확인한다. 원본 이미지 다시 보기 및 재분석도 확인한다.
4. 가계부 분석 후 `/api/statistics/ai-analysis/history/{id}`의 `history.status=COMPLETED`, `result`가 채워지는지 확인한다. 화면의 처리 중 표시가 해제되는지 확인한다.
5. 기존 PROCESSING 작업은 저장된 복구 입력과 작업 소유권을 기준으로 기존 복구 스케줄러가 재시도한다. 이미 FAILED인 기록은 자동 재시도하지 않으므로 재분석이 필요하다. 원본 이미지 참조 저장 전에 실패한 경우 이미지를 다시 업로드해야 할 수 있다. 잃어버린 과거 LLM 응답을 복원한 것은 아니다.
6. 실제 MariaDB·MinIO·모델 서버의 통합 호출과 운영 지연 시간은 이번 로컬 테스트로 검증한 범위가 아니다. 운영에서는 작업 대기 시간, 제공자 추론 시간, 결과 저장 및 조회 시간을 구분해 확인한다.
