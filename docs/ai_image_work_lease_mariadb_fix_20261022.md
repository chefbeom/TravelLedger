# 이미지 동시 분석 작업 소유권 오류 수정 (2026-10-22)

## 증상과 원인

- 이미지 3건을 동시에 분석하면 1건만 성공하고 다른 요청은 `작업 소유권 저장소에 연결할 수 없습니다`로 실패했다.
- 기존 `WorkLeaseService`는 짧은 `REQUIRES_NEW` 트랜잭션에서 만료된 행을 `UPDATE`하고 없으면 `INSERT`했다. 격리 수준은 MariaDB 기본 `REPEATABLE READ`를 그대로 사용했다.
- VM의 별도 MariaDB 11.4.13에서 **변경 전 코드 그대로 3건 중 1건 성공·2건 실패**를 재현했다. 실제 `UPDATE` 완료 시점을 정렬했을 뿐, SQL 오류를 주입하지 않았다.
- JDBC 로그의 오류는 `1213 / SQLSTATE 40001`(deadlock)이었다. 같은 임시 DB의 `SHOW ENGINE INNODB STATUS`에서도 PRIMARY 인덱스의 supremum/gap 잠금과 INSERT intention 잠금 교착이 확인됐다. 서로 다른 `image-job:*` 키도 같은 인덱스 간격에 있으면 발생할 수 있다.
- 모든 `DataAccessException`을 동일한 연결 오류 문구로 바꾸면서 원인도 버려, 실제 접속 장애와 잠금 충돌을 구분하지 못했다. 운영 서버의 원인 로그를 직접 확인한 것은 아니며, VM에서 동일 증상과 코드 결함을 재현한 결과다.
- H2에서만 수행했던 기존 동시성 검증은 이 InnoDB 잠금 동작을 포착하지 못했다.

MariaDB의 격리 수준별 잠금 설명: [SET TRANSACTION 공식 문서](https://mariadb.com/docs/server/reference/sql-statements/administrative-sql-statements/set-commands/set-transaction).

## 수정 범위

- 작업 소유권 전용 `REQUIRES_NEW` 트랜잭션에만 `READ COMMITTED`를 지정했다. 애플리케이션/DB 전역 격리 수준과 거래 데이터의 트랜잭션 설정은 바꾸지 않는다.
- 기존 조건부 만료 갱신, PRIMARY KEY, 소유자 토큰 검사, heartbeat, 만료, 반환 규칙은 유지한다. 동시 분석 기본값 3건과 관리자 설정도 유지한다.
- 교착/잠금 대기 오류만 전체 트랜잭션 단위로 최대 3회 시도한다. 실패한 트랜잭션이 롤백된 다음, 짧은 지연과 jitter를 두고 새 트랜잭션을 시작한다. 일반 획득과 시간 간격 예약 모두 같은 정책을 사용한다.
- 중복 키는 기존처럼 `null`/`false`(다른 작업이 소유 중)로 처리한다. DB 접속/권한 오류는 반복하지 않으며 소유권 없이 작업을 진행하지 않는다.
- 재시도 중 취소/인터럽트는 유지한다. 충돌 소진과 저장소 오류의 사용자 문구를 구분하고 원인 예외를 보존한다. 진단 로그에는 시도 횟수·예외 유형·SQLSTATE·벤더 오류 코드만 기록하며 SQL/매개변수/소유자 토큰은 추가로 기록하지 않는다.
- 스키마와 API 형식 변경, 신규 마이그레이션, AI 요청 내용 변경은 없다.

## 재현 테스트

`WorkLeaseMariaDbIntegrationTest`는 환경변수로 명시적으로 켜는 테스트다. 루프백 주소의 `calen_lease_verify_*` 전용 스키마만 허용하고, 해당 임시 스키마에서만 테이블을 만들거나 초기화한다. 일반 CI에서는 환경변수가 없으므로 실행하지 않는다.

필요한 환경변수:

- `CALEN_LEASE_TEST_JDBC_URL`: `jdbc:mariadb://127.0.0.1:<포트>/calen_lease_verify_<식별자>`
- `CALEN_LEASE_TEST_USER`, `CALEN_LEASE_TEST_PASSWORD`: 임시 DB 전용 계정

임시 MariaDB의 `innodb_lock_wait_timeout`은 잠금 대기 회귀 테스트를 위해 3초로 설정한다. 실제 앱 또는 운영 DB를 이 테스트에 연결하지 않는다. 실행 대상은 `test --tests '*WorkLeaseMariaDbIntegrationTest'`다.

## 검증 기록

- 사용자 승인에 따라 `192.168.35.123`에 **별도 임시 MariaDB 컨테이너**를 만들었다. VM의 기존 앱·MariaDB·Redis·MinIO 컨테이너, 기존 DB와 운영 데이터는 변경하지 않았다.
- 임시 DB는 VM 루프백 포트만 열고 SSH 터널로 연결했다. 저장소는 tmpfs이며 임시 전용 계정을 사용했다.
- 변경 전: 같은 인덱스 간격에서 동시에 소유권을 확보하면 **성공 1 / 실패 2**, MariaDB `1213/40001`.
- 변경 후: 같은 조건에서 **성공 3 / 실패 0**. 두 서비스 인스턴스의 12건 처리도 **최대 동시 3건**, 12건 모두 완료하고 잔여 소유권 0건.
- 같은 키 12건 경합에서는 소유자가 정확히 1명이며, 만료 후 교체된 소유권을 이전 소유자가 삭제하지 못함을 확인했다.
- MariaDB + Hikari + JpaTransactionManager 조합의 3건 동시 획득을 확인했다. 호출자의 `REPEATABLE READ` 트랜잭션과 풀 반환 후 연결 기본값이 그대로 유지됨도 확인했다.
- H2에서 교착/잠금 대기 롤백 후 새 연결 재시도, 재시도 상한, 연결/권한 오류 미재시도, 원인 보존, 취소 및 호출자 격리를 검증했다.
- 임시 MariaDB에서 실제로 행 잠금을 유지해 `1205/HY000` 잠금 대기 오류를 발생시켰다. 차단 트랜잭션을 해제한 뒤 새 트랜잭션 재시도로 정상 획득·반환하며 잔여 소유권 0건임을 확인했다.
- 관련 AI 작업 저장·취소·복구, OCR, 제공자 큐, 관리자 설정 권한, 지도 검색, 임베딩 및 구조 계약 회귀 테스트도 수행했다.
- 최종 실행: **158건 통과 / 실패 0 / 오류 0 / 건너뜀 0**. 이 중 실제 MariaDB 검증은 5건이다.
- 실제 외부 AI API 호출이나 기존 VM 앱 교체 배포는 하지 않았다. 따라서 이 결과는 소유권/동시 실행 계층의 실제 MariaDB 검증이며, 운영 AI 전체 흐름의 실호출 검증을 의미하지 않는다.

- 검증 후 이번에 만든 `calen-lease-verify-20261022` 컨테이너만 작업 라벨과 정확한 이름을 확인하고 삭제했다. tmpfs의 임시 DB와 데이터도 함께 제거됐으며 보존 대상 데이터는 없다. SSH 터널도 종료했다. 기존 VM 서비스는 그대로 실행 중임을 확인했다.
- 코드·테스트·문서 변경은 로컬에 남겼으며 커밋·푸시는 별도 요청 시 진행한다.
