# 백엔드 MVC·헥사고널 리팩토링 진행

## 목표와 보존 조건

2026-10-15 백엔드 구조 분석 및 MVC·헥사고널 설계 논의를 구현한다. 단일 배포·기능별 패키지는 유지한다. API 주소·JSON 계약, 소유권·공유 권한, 기존 DB·마이그레이션, 트랜잭션·잠금·버전, 캐시 무효화, 비동기 복구와 파일 보상 처리를 보존한다. 기존 미커밋 기능·문서 변경을 덮어쓰지 않는다. 커밋·푸시는 별도 요청 시에만 수행한다.

## 의존 규칙

- `domain`: 업무 값·상태·정책. Spring/JPA/Jackson/HTTP/SDK 또는 다른 기능의 영속 엔티티를 참조하지 않는다.
- `application/port/in`: 유스케이스와 입력 계약. HTTP DTO·인증 principal을 참조하지 않는다.
- `application/port/out`: 필요한 저장·외부 기능의 계약. JPA Entity/Repository·HTTP 클라이언트를 노출하지 않는다.
- binary 입력 선언의 I/O 예외는 `LedgerImageStoragePort.Upload`의 JDK `InputStream`/`IOException`, `TravelRouteUploadPort.Upload`의 `IOException`에만 한정한다. GPX는 기존 MultipartFile.getBytes 시점·checked 오류를 보존하기 위한 선언이며 스트림/파일 접근을 허용하지 않는다. 두 계약은 abstract 메서드만 가지며, application/domain의 직접 파일/네트워크 I/O를 허용하지 않는다. 컴파일 의존 규칙과 반례 검사로 범위를 고정한다.
- `application/service`: 포트·업무 모델로 업무 흐름을 조정한다. 직접 DB·네트워크·직렬화에 접근하지 않는다.
- `adapter/in`: HTTP 매핑·트랜잭션 진입·기존 호출자 호환. 요청 전체를 포괄해야 하는 DB 잠금은 같은 트랜잭션에 둔다.
- `adapter/out`: 기존 서비스/DB/외부 API 연결, 모델 변환, 직렬화, 잠금 구현.
- 기존 `web/service/repository/domain/dto`는 전환하지 않은 업무의 경계다. 새 코어가 기존 DTO·영속 엔티티에 의존하지 않도록 점진적으로 대체한다. 기존 DTO 및 DB 구조의 일괄 이동은 하지 않는다.
- 공통 예외는 현재 프레임워크 독립적인 `common.exception`의 업무 실패 타입을 사용한다. 서비스별 interface/Impl을 일괄 생성하지 않는다.

## 공유 요청 생성의 검증 항목

- 기존 HTTP URI·필드·상태 코드와 공유 스냅샷 JSON 포맷 보존.
- 원본/수정 공유, 공유 메모, 원본 보존, 여행 참조 공유 보존.
- 활성 사용자 및 그룹 접근, 타인 원본/분류/결제수단 거부.
- 원본 잠금 후 수신자 공유 행 잠금 순서 유지. 여러 수신자 중 실패 시 전체 롤백.
- 동일 요청 재시도, 대기/승인된 거래 덮어쓰기 방지, 취소 후 재공유.
- 실제 HTTP 경로에서 트랜잭션 적용, 승인·재공유 경합 검증.
- 새 코어/포트에서 프레임워크·레거시 DTO·영속 엔티티 의존 금지.

## 작업 기록

- 시작 시 현재 워킹 트리 확인: 기존 수정 공유 기능과 관련 테스트/프런트 변경, 그 외 사용자 변경이 존재한다. 기존 변경을 보존하고 새 리팩토링 변경만 추가한다.
- 단계별 시점의 상태는 아래에 그대로 보존한다. 최종 판정은 [목표별 최종 감사](backend_refactoring_acceptance.md)를 기준으로 하며, 점진적 구조 개선 완료와 미전환 기존 업무·별도 운영 검증을 구분한다.

### 2026-10-15: 공유 요청 생성 수직 단위

- HTTP Controller를 `sharing/adapter/in/web`로 이동하고 생성 요청이 `CreateRecordShareUseCase`를 직접 호출하도록 연결했다. URI·요청 검증·응답 DTO는 유지했다. 조회·승인·취소는 아직 기존 서비스에 남는다.
- `application/service/CreateRecordShareService`가 공유 방식·메모·수신자 중복·기존 요청 재사용 판단을 조정한다. `domain/policy/ShareCreationPolicy`가 수정 여행 공유 금지, 메모 길이, 대기/승인 요청 보존 규칙을 소유한다.
- 참가자/그룹, 원본 조회, 공유 요청 저장을 세 출력 포트로 분리했다. 포트의 값 모델은 Spring/JPA/Jackson·다른 기능의 DTO/영속 엔티티를 참조하지 않는다.
- `TransactionalCreateRecordShare`가 그룹 검사부터 모든 수신자 저장까지 하나의 트랜잭션을 유지한다. JPA 출력 어댑터는 `MANDATORY`로 트랜잭션 없는 호출을 거부한다. 원본 잠금 → 수신자 공유 행 잠금 순서를 유지했다.
- 스냅샷 인코딩은 기존 `LedgerEntryResponse` 계약을 어댑터에서 사용한다. 외화 소수점·필드 순서·`HH:mm` 등 기존 JSON과 바이트 단위로 일치하는 테스트를 추가했다. 코어에는 JSON 대신 불변 값과 불투명 동등성 토큰만 전달한다.
- 기존 `RecordSharingService.create`는 내부 호출자 호환을 위해 동일 입력 포트에 위임한다. 생성 판단 로직을 복제하지 않았다.
- Spring 없이 실행하는 유스케이스 테스트 9건, 스냅샷 계약 테스트 3건, 컴파일된 메서드 본문·제네릭 서명까지 확인하는 아키텍처 테스트 2건을 추가했다. 아키텍처 검사는 아직 전환한 공유 코어만 대상으로 하며, 전체 기존 백엔드가 새 경계를 지킨다고 주장하지 않는다.
- H2 실제 트랜잭션으로 동시 생성의 중복 방지, 승인과 다른 그룹 재공유의 경합, 다중 수신자 실패 시 신규 행 및 기존 취소 행 변경의 전체 롤백, 출력 어댑터의 트랜잭션 강제를 검증했다. MariaDB 격리 수준·특화 SQL 검증을 대체하지는 않는다.
- 공유·거래·정기결제·여행 접근 관련 회귀 98건 통과. 이후 전체 `gradlew test` 결과 **100개 테스트 스위트, 551건, 실패 0 / 오류 0 / 건너뜀 0**, `BUILD SUCCESSFUL` (2분 35초)을 확인했다. 파라미터화 실행이 있어 테스트 선언 수와 실행 수는 다르다.
- 전체 회귀 실행의 기본 DB를 H2 메모리 DB로 지정하고 외부 Redis·MinIO·임베딩·운영 백업 연결을 비활성화했다. 별도 설정이 있는 테스트 역시 테스트 DB·모의 객체를 사용했다. 운영 데이터 변경은 수행하지 않았다.
- 시크릿 스캔, 새 코드의 UTF-8 BOM·후행 공백 검사, 기존 수정 파일의 `git diff --check` 통과. 새 의존성·DB 마이그레이션·운영 설정 변경은 없다.
- `gradlew bootWar` 성공. 생성 WAR에 이동한 Controller, 트랜잭션 진입 어댑터, 유스케이스 구현이 포함되고 이전 `sharing/web/RecordShareController` 클래스가 남지 않은 것을 확인했다. 배포·커밋·푸시는 수행하지 않았다.

### 2026-10-15: 거래 입력 준비·기록 지도 쓰기 확장

- 가계부의 생성·수정·수정 공유 미리보기에서 사용하는 입력 준비를 `PrepareLedgerEntryUseCase`로 연결했다. 코어는 소유자 범위의 분류/소분류·결제수단, 외화 환산, 여행 기간을 검사하고 불변 `Prepared` 값을 반환한다. JPA·기존 환율 서비스는 출력 어댑터 안에만 둔다.
- 제목·메모 정규화는 `LedgerTextPolicy`, 통화 코드·외화 4자리·환율 6자리·원화 0자리 HALF_UP 계산은 `LedgerMoneyPolicy`가 소유한다. 기존 Excel/CSV 호출자는 호환 래퍼를 통해 같은 텍스트 정책을 사용한다.
- `LedgerEntryService`의 생성·수정·이력·삭제·조회 트랜잭션은 이동하지 않았다. 입력 준비 어댑터와 참조 어댑터는 `MANDATORY`로 기존 트랜잭션에 참여하고, 검증된 엔티티 참조는 같은 영속성 컨텍스트에서 재사용한다. 환율 서비스의 호출 시점도 기존과 같으며 모든 외부 연동을 트랜잭션 밖으로 옮긴 단계는 아니다.
- 수정 공유의 외화 환율 명시, 원본/이력 불변, 여행 연결 제거, 수입 미리보기에서 보조 결제수단조차 생성하지 않는 규칙을 유지했다. 일반 수입 저장의 결제수단 생성 규칙은 출력 어댑터에 한 곳만 남겼다.
- 기록 지도 장소·모음·방문 기록의 생성/수정/삭제, 여행 원본 가져오기를 `WriteRecordMapUseCase`와 두 출력 포트로 분리했다. 방문이 있는 장소의 삭제 제한, 다른 장소로 방문 기록 이동 금지, 소유자 범위의 모음 검증, 가져오기 시 길이·좌표 검증은 코어/정책이 담당한다.
- 기록 지도 HTTP Controller를 `adapter/in/web`로 옮기고 쓰기 API가 입력 포트를 직접 호출하도록 연결했다. 기존 DTO·URI·상태 코드·응답 필드는 유지한다. 기존 `RecordMapService` 쓰기 메서드는 내부 호출자 호환 위임만 하며 판단 로직을 복제하지 않는다. 지도 조회/공개 조회·방문 조회·여행 후보 조회는 아직 기존 서비스에 남아 있다.
- 쓰기 어댑터가 요청 전체를 하나의 트랜잭션으로 묶는다. JPA 어댑터는 `MANDATORY`를 요구한다. 여행 원본 잠금 → 중복 확인 순서, 방문 삭제의 행 잠금, 기존 `@Version` 엔티티와 같은 영속성 컨텍스트, 공유 링크 삭제/flush → 모음 연결 해제 → 모음 삭제 순서를 유지했다.
- 재가져오기는 모음 소속만 추가하며 사용자가 수정한 장소 이름·메모·좌표를 덮어쓰지 않는다. 방문 사진 DB 삭제는 같은 트랜잭션에 참여하고, 실제 파일 삭제는 기존 `afterCommit` 보상 경로를 그대로 사용한다.
- Spring 없이 실행하는 가계부 입력 준비 테스트 8건과 기록 지도 쓰기 테스트 10건을 추가했다. 기록 지도 H2 통합 테스트 4건을 더해 비소유 모음 편집 거부/원본 보존, 다른 장소 방문 편집 거부, 파일의 커밋 전 보존·롤백 복원·커밋 후 삭제, 동시 여행 가져오기 및 재가져오기 보존, 트랜잭션 없는 출력 어댑터 호출 거부를 검증했다.
